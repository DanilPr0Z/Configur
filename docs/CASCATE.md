# Интеграция с cascate.ru

Выгрузка панелей заказа во внешнюю систему `cascate.ru`.

---

## Схема

```
React (OrderDetail)          Django                    cascate.ru
─────────────────────────────────────────────────────────────────────
[Выгрузить в Cascate]
  login + password  ──POST──▶ /api/orders/{id}/
                              export_cascate/
                                    │
                                    │  token из .env
                                    ├──POST──▶ /Api/login/     → id_person
                                    │
                                    ├──POST──▶ /Api/addPanel/  → id_panel
                                    ├──POST──▶ /Api/addPanel/     (по одной
                                    └──POST──▶ /Api/addPanel/      на панель)
                                    │
  {sent, skipped,   ◀──────────────┘
   failed, errors}
```

**Почему через бэкенд, а не напрямую из браузера.** Две независимые причины:

1. `CASCATE_TOKEN` — общий токен приложения. Из фронта он попал бы в JS-бандл и стал бы публичным.
2. `cascate.ru` отдаёт `Access-Control-Allow-Origin: http://dgv.cascate.ru` — браузер всё равно не пустил бы запрос с нашего домена.

---

## Настройка

`.env` (файл в `.gitignore`, в репозиторий не попадает):

```env
CASCATE_BASE_URL=https://cascate.ru/Api
CASCATE_TOKEN=<токен приложения>
CASCATE_TIMEOUT=20
```

Без `CASCATE_TOKEN` эндпоинт вернёт `500 {"error": "CASCATE_TOKEN не задан в .env"}`.

Зависимость: `requests==2.32.3` (в `requirements.txt`).

## Особенности внешнего API

Выяснены экспериментально — письменной спецификации от их стороны нет.

| Что | Почему важно |
|-----|--------------|
| **Слеш в конце URL обязателен** | Без него Apache отдаёт `301` на версию со слешем. Редирект превращает `POST` в `GET`, и тело запроса теряется молча. Поэтому клиент ходит на `/Api/login/`, а не `/Api/login`, и выставляет `allow_redirects=False` — явная ошибка лучше потерянной панели. |
| **`application/x-www-form-urlencoded`**, не JSON | На той стороне PHP. |
| **Сервер выдаёт `PHPSESSID`** | Клиент держит `requests.Session`, чтобы кука с `login/` доехала до `addPanel/` — на случай если он смотрит на сессию, а не только на `id_person`. |
| **Ответ отдаётся с `Content-Type: text/html`** | Тело при этом JSON. `resp.json()` на content-type не смотрит, так что разбор работает. |
| **Ключ ошибки — то `error`, то `mag`** | Опечатка на их стороне (`mag` вместо `msg`), см. ниже. |

### Разбор ответа

Ответы на ошибках проверены на живом `cascate.ru`:

| Что не так | Ответ | Как разбираем |
|---|---|---|
| Неверный логин/пароль | `{"success":false,"mag":"Error auth"}` | `CascateAuthError` → `401` |
| Неверный или пустой токен | `{"success":false,"error":"Не верный токен!"}` | `CascateTokenError` → `500` |

**Ключ `mag` — опечатка на их стороне** (должно быть `msg`). Он в списке
`_ERROR_KEYS`; если Костя однажды её исправит, `msg` там уже есть, ничего не сломается.

Токен отличается от пароля по слову `токен` / `token` в тексте ошибки. Различие
важное: неверный токен — это наш `.env` (чинит разработчик, `500`), неверный
пароль — это ввод пользователя (`401`). Одинаковый код заставил бы пользователя
перебирать пароли при сломанном конфиге.

**Формат успешного ответа всё ещё не подтверждён.** `id` ищется в нескольких
вероятных ключах, в том числе завёрнутый в конверт (`{"data": {...}}`):

- `id_person` ← `id_person` / `idPerson` / `person_id` / `personId` / `id`
- `id_panel` ← `id_panel` / `idPanel` / `panel_id` / `panelId` / `id`

Если `id_person` не нашёлся ни под одним ключом — клиент падает с телом ответа
в тексте ошибки. Это сделано намеренно: первый живой запуск сразу покажет
реальный формат вместо того, чтобы тихо записать `None`.

## Эндпоинт

### `POST /api/orders/{id}/export_cascate/`

**Тело:**

| Поле | Тип | Обяз. | Описание |
|------|-----|-------|----------|
| `login` | string | да | Логин пользователя в cascate.ru |
| `password` | string | да | Пароль. Не сохраняется и не попадает в логи и тексты ошибок |
| `force` | bool | нет | Отправить заново уже выгруженные панели |

**Ответ `200`:**

```json
{
  "id_person": "777",
  "sent": 3,
  "skipped": 0,
  "failed": 1,
  "errors": [{"panel": "Панель #2", "error": "addPanel: panel rejected"}]
}
```

**Коды ошибок:**

| Код | Когда |
|-----|-------|
| `400` | Не передан логин или пароль |
| `401` | cascate.ru отверг логин/пароль пользователя |
| `500` | `CASCATE_TOKEN` не задан или отвергнут cascate.ru |
| `502` | cascate.ru недоступен, вернул не-JSON или HTTP 5xx |

Частичный сбой — это `200`: часть панелей ушла, часть в `errors`. Транзакции нет,
откатить уже отправленное невозможно, поэтому статус отражает «что-то доехало».

## Идемпотентность

**Проблема.** Неизвестно, дедуплицирует ли `addPanel` на своей стороне.
Наивная реализация при втором нажатии кнопки создала бы дубли всех панелей.

**Решение.** У `Panel` и `DoorPanel` есть `cascate_synced_at`. Панель с непустой
отметкой пропускается (`skipped`), если не передан `force=true`.

Признаком выгрузки служит **`cascate_synced_at`, а не `cascate_id`** — внешний API
может не вернуть `id_panel`, но панель при этом уже создана. Если бы признаком был
`cascate_id`, такая панель уехала бы повторно.

Следствия:

- Повтор после успеха → `sent: 0, skipped: N`, ни одного `addPanel`.
- Повтор после частичного сбоя → досылаются **только упавшие** панели.
- `force=true` → перезалив всех. В UI под галочкой с предупреждением про дубли.

## Поля `addPanel`

Состав не был согласован («остальные поля от твоей реализации»), поэтому шлём
плоский набор скаляров, покрывающий модель целиком. Числа — строкой с точкой,
два знака после запятой.

**Общие для заказа:** `source='nuovo60'`, `order_id`, `order_number`,
`invoice_number`, `customer_name`, `agent_name`, `counterparty`, `city`.

**Общие для панели:** `external_id` (`panel-{id}` / `door-{id}` — подсказка
принимающей стороне для дедупликации), `panel_type` (`wall` / `door`),
`position`, `wall_number`, `quantity`, `height`, `width`, `area`,
`finish_group`, `finish`, `veneer_direction`, `decor_name`,
`markup_percent`, `cost`, `notes`.

**Только стеновая (`panel_type='wall'`):**
`joint_left`, `joint_right`, `joint_top`, `joint_bottom` — коды узлов (`A`, `DG`, …),
`aluminum_vertical_count`, `aluminum_horizontal_count`, `aluminum_color`.

**Только дверная (`panel_type='door'`):**
`door_order_number`, `opening_width`, `opening_height`, `ceiling_height`,
`mount_type`, `opening_direction`,
`joint_top_left`, `joint_top_right`, `joint_bottom`,
`edge_left`, `edge_right`, `edge_top`, `edge_bottom`.

`cost` = `panel.total_cost`: отделка с наценкой + стоимость узлов, за всё
количество, без НДС.

## Что проверено

На локальном мок-сервере (настоящий HTTP-транспорт, настоящий DRF-эндпоинт):

- успешная выгрузка; не-JSON ответ; HTTP 500;
- поимка `301` при URL без слеша;
- повтор без дублей (0 новых `addPanel`); `force` (все заново);
- частичный сбой (2 из 3 выгрузились); досыл только упавшей панели;
- пароль не попадает в текст ошибок.

На живом `cascate.ru`:

- токен из `.env` принимается (`login` с ним доходит до проверки пароля);
- неверный пароль → `CascateAuthError` → `401`;
- неверный токен → `CascateTokenError` → `500`.

**Успешный путь против живого `cascate.ru` не проверялся** — нет учётной записи.
Не подтверждены: формат успешного ответа `login` (где лежит `id_person`), формат
ответа `addPanel`, и читает ли их сторона наши поля. При несовпадении клиент
упадёт с телом ответа в тексте ошибки, а не запишет мусор.
